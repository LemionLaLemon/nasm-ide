# NASM IDE

> [!IMPORTANT]
> This project was entirely vibecoded aside from the two repos that were forked.
> README was reviewed by a human but that's about it.

Language support for **64/32-bit x86 NASM assembly** in VS Code and
code-oss (Open VSX): IntelliSense, hover docs, cross-file `extern`
navigation, library-aware diagnostics, doc comments, and one-command builds.

Fork origins:
[vscode-nasm-intellisense](https://github.com/Alec269/vscode-nasm-intellisense)
by Nomayer Alam (Alec269, MIT), with ideas from
[asm-lsp](https://github.com/bergercookie/asm-lsp) (Berger Cookie, BSD-2).
The server, grammar, instruction database, and all features below were
substantially extended here. License: MIT, see `LICENSE.md`.

## Features

- ~190 instructions with unabbreviated names (`jae` - *Jump if Above or
  Equal*), 136 registers, SSE/AVX scalar float, core x87 FPU, directives.
- Labels, section names, `global`/`extern`/`equ`/`%define` symbols, and all
  other symbolic words scoped as `entity.name.function` (yellow in most
  dark themes; force it everywhere with the snippet below).
- 57 common libc functions (`printf`, `malloc`, `memcpy`, …) with C
  signatures and link hints (`-lc` vs `-lm`).
- Autogenerated docs for other configured libraries (X11, …): prototypes
  from their headers, summaries from man pages (see below).
- `struc` support: member completion after `Name.`, hover with computed
  offsets/sizes, cross-file goto-def, auto `Name_size` (see below).
- `.bss`/`.data` symbols: `name resb N` / `name db ...` complete, hover
  (with sizes), and jump to definition, same-file or via `global`+`extern`.
- Doc comments above labels and `equ` constants (see below).
- As-you-type (debounced) or on-save diagnostics.
- `NASM IDE: Pick Link Libraries` - fuzzy-search every linkable `-l` flag
  on your system, saved to the workspace.
- gdb debugger: source/instruction breakpoints, registers, flags, `.data`/`.bss`
  globals, stack, call stack, disassembly, memory, restart. Launch in a terminal
  for ncurses and X11, or in the Debug Console for headless programs (see below).

## Library documentation

Anything in `nasmIde.libraries` gets hover/completion docs, not just libc:

1. The `-l` flag is matched to its `.pc` file (`pkg-config`), which gives
   the library's include dirs.
2. Headers there are scanned for C prototypes (single- and multi-line;
   macros, typedefs, and internals skipped).
3. A prototype is kept only if the library itself exports that symbol
   (`nm -D` check), so shared include trees can't misattribute functions.
4. One-line summaries come from `man 3` / `man 2`, looked up lazily and
   cached; parameters render with System V AMD64 registers like libc.

Header-declared symbols also count as "provided" for unresolved-`extern`
warnings (covers `static inline` helpers with no `nm` entry). Libraries
without a `.pc` file (like bare `-lc`) only get `nm`-based quieting.

## Doc comments

```nasm
; Adds two numbers.
; @param eax 32 bit signed integer
; @param ebx dword second operand
; @return eax the sum
addition:
```
Force symbol yellow in any theme (`settings.json`):

```json
"editor.tokenColorCustomizations": {
    "textMateRules": [
        { "scope": "entity.name.function.nasm", "settings": { "foreground": "#DCDCAA" } },
        { "scope": "keyword.control.flow.push.nasm", "settings": { "foreground": "#89D185" } },
        { "scope": "keyword.control.flow.pop.nasm", "settings": { "foreground": "#C586C0" } }
    ]
}
```

## Structs

`struc` blocks are parsed: fields (with computed byte offsets and sizes),
`equ` constants, padding, and alignment.

- Member completion after `Name.` (or filtered, `Name.w`), with
  `dword field @ +8`-style details.
- Hover shows offset and size (`Field of struc \`Button\` — offset 8,
  4 bytes (dword)`), constants show their value.
- Go-to-definition jumps to the member line, across files.
- Every struc gets its NASM-auto `Name_size` constant (completed,
  hoverable, jumpable).

## Stack checking

`push`/`pop` families are highlighted distinctly, and the server pairs them
along the function's control flow (local labels, `jmp`, and conditional jumps
are followed):

- `pop` with a provably empty stack on every path reaching it, or `ret` with
  pushes never popped: **error**.
- Pushes left over at a return/tail jump: **error** on that line (the "can't
  find its pair" dark red).
- A branch that skips the normal epilogue and pops on its own path is fine:
  `.failed: pop rbx / pop rbp / ret` reached via `jc .failed` is valid even
  though an earlier `pop` exists in the fall-through path.

### Pair colors (FILO)

Every push gets the next color in a 6-color cycle; each pop wears its
matching push's color (nesting-adjacent depths are maximally separated).
Unmatched pops and pushes keep their normal instruction color plus the red
squiggle. Colors are user-configurable (`settings.json`):

```json
"editor.semanticTokenColorCustomizations": {
    "rules": {
        "*.pair0": "#4EC9B0",
        "*.pair1": "#61AFEF",
        "*.pair2": "#E06C9E",
        "*.pair3": "#D19A66",
        "*.pair4": "#56B6C2",
        "*.pair5": "#A9DC76"
    }
}
```

This is a pairing heuristic, not a verifier: joins take the shallowest path,
so genuinely conflicting paths are reported conservatively. Disable
per-workspace with `nasmIde.diagnostics.stackCheck: false`.

- Tags: `@param [size] name desc`, `@return [size] [name] desc`.
- Sizes: `byte word dword qword tword oword yword zword`, `N bytes`
  (before or after the name).
- Prefixes: `;`, `;;`, `; @`, `;---@` all work; `;---` separators and blank
  lines end the block; `global`/`extern` lines are transparent to it.
- Shows on hover (at the definition and at every `call`) and in completions.

## Commands / tasks

- `NASM IDE: Restart Language Server` · `Show Server Status` ·
  `Toggle Diagnostics` · `Pick Link Libraries` ·
  `Configure Debugging`
- `Configure Debugging` writes `.vscode/launch.json` and `.vscode/tasks.json`
  for the current workspace. It detects a Makefile target, or falls back to the
  extension's build output, and keeps any existing configurations.
- Tasks: `NASM IDE: build` (default build, `Ctrl+Shift+B`), `run`, `clean`,
  and `make` (runs the workspace `Makefile`; also the default pre-launch task
  when a Makefile exists). A `tasks.json` file is optional: the extension
  provides these tasks automatically.

## Debugging
Press **F5** and pick **NASM (gdb)**; or run
**NASM IDE: Configure Debugging** from the Command Palette to create the
files for you. The command is the quickest way to set up a new project:

1. Open the project root (the folder containing `Makefile` or `src/`).
2. Run **NASM IDE: Configure Debugging**.
3. Press **F5**.

For a Makefile project, it uses `NASM IDE: make`; otherwise it uses the
extension's `NASM IDE: build` task. You can also add a configuration by hand:

```jsonc
{
    "type": "nasm",
    "request": "launch",
    "name": "Debug NASM program",
    "program": "${workspaceFolder}/build/deforest", // unstripped ELF
    "cwd": "${workspaceFolder}",
    "console": "integratedTerminal", // ncurses/X11/interactive
    "stopOnEntry": true,
    "preLaunchTask": "NASM IDE: make"
}
```

`console` can be `integratedTerminal` (default), `externalTerminal`, or
`internalConsole`. Terminal modes run the program under `gdbserver`; the
Debug Console mode runs gdb directly with piped stdin/stdout. For ncurses
programs keep the integrated/external terminal, and debug the output that
keeps its DWARF symbols (not a `-stripped` binary).

The Debug Console accepts gdb commands such as `x/16gx $rsp` and
`info registers`. Register, flag, `.data`/`.bss`, and `rsp` scopes refresh on
each stop. The Data scope reads variable sizes from your NASM declarations, so
strings and `resb`/`resd` buffers get sensible values; arrays expand into a
byte view, and labels like `Window:` group their `.field` children.
Registers and data variables are editable: double-click a value in the
Variables view. Registers accept gdb expressions; data accepts numbers,
comma-separated elements, quoted strings, or hex byte lists such as
`68 69 00`. Breakpoints can be conditional or have a hit count. To attach to
an already running program, use a `"request": "attach"` configuration with
either `processId` or `host`/`port` (gdbserver).

Make sure `gdbserver` is installed and on `PATH` (on Debian/Ubuntu it is in
the `gdbserver` package). Override paths with `gdbPath` / `gdbserverPath`.

## Configuration (`nasmIde`)

| Key | Default | What |
| --- | --- | --- |
| `nasmPath` | `"nasm"` | Assembler executable for diagnostics |
| `arch` | `"x86_64"` | `elf64` vs `elf32` diagnostics format |
| `diagnostics.enable` | `true` | Master switch |
| `diagnostics.mode` | `"asYouType"` | Or `"onSave"` |
| `diagnostics.debounceMs` | `400` | As-you-type delay |
| `diagnostics.unresolvedExterns` | `true` | Warn on unknown `extern` |
| `libraries` | `["c"]` | `-l` flags (folder scope, use the picker) |
| `build.linker` | `"ld"` | Or `"gcc"` |
| `build.sources` | `["src/*.asm"]` | Globs relative to the folder |
| `build.objDir` | `"obj"` | Intermediate `.o` dir |
| `build.output` | `"bin/${workspaceFolderBasename}"` | Linked binary |
| `build.extraLdFlags` | `[]` | e.g. `["-dynamic-linker", "/lib64/ld-linux-x86-64.so.2"]` |

## Developing

```sh
npm install && cd server && npm install && cd ..
npm run compile   # tsc client + server
npm test          # unit + LSP integration + headless client tests
npm run package   # nasm-ide-*.vsix
```
